### B1 root cause and fix

Codex on Windows reads console key events. The bundled ConPTY strips the bracketed-paste markers (confirmed with a fixture: no `ESC[200~` reaches a key-event reader), so Codex sees a fast key burst and applies its paste-burst heuristic: characters within 8 ms form a burst, shown after 60 ms of quiet, and **an Enter processed within 120 ms of the burst's last character inserts a newline** instead of submitting. "Within" is measured when Codex *processes* the key. `pod send` pressed Enter 30 ms after the text (always inside the window: the cli.log failure) and review delivery 250 ms after the paste (inside the window whenever Codex lags behind a ~600-char paste: d1/d2). Screenshot 16 shows the trailing newline the Enter produced.

Fix (`crates/podd/src/server/submit.rs`, shared by `terminal.send` and review delivery): press Enter only after the program has drawn the text and been quiet for 300 ms (min 150 ms; 1 s if nothing is drawn; bounded by 1 s + 0.5 ms/char, max 5 s). Under CPU load the quiet period adapts: if the program's output paused up to *g* ms since the write (write to first draw, or between draws of a burst drawn in pieces), Enter waits for *g* ms of quiet (at least 300 ms), and a program that paused longer than 300 ms gets the full 5 s bound (daemon log: `lagging program (output paused up to … ms)`). Then, for terminals with a visible agent status, require a turn start (working/blocked, or the turn counter advanced) within 4 s; otherwise press Enter once more and check again. The outcome is reported separately from transport delivery: `SubmitCheck {state: pending|confirmed|unconfirmed|unverifiable, enters, signal}` in `SendResult.submit`, `ReviewDeliveriesResult.submits` and a second `review.delivery` event carrying `submit`. `pod send` warns on `unconfirmed`; `--no-confirm` opts out. `DeliveryInfo` is unchanged because pod-app constructs it literally.

Tests: `fake-agent burst-loop` reads console key events through the bundled ConPTY and applies Codex's burst rules, with an optional per-key processing lag. Against it the old timings fail (30 ms `pod send`: never submitted; 250 ms review paste: not submitted at ≥0.1 ms/key lag). `tests/submit.rs`: send submits once (Enter ×1, confirmed), 0.3 ms/key lagging TUI with a 30-line text, missed Enter retried once (Enter ×2, confirmed), an agent that never reacts → `unconfirmed` after Enter ×2, shell → `unverifiable`. `tests/orchestration.rs::review_delivery_submits_to_a_lagging_paste_burst_tui` (1.5 KB+ prompt, exactly one submission byte-equal to the prompt, `submits` + confirmation event). `server::submit` unit tests. Load robustness (branch `SJin-Choi/flaky-submit`): under heavy CPU load the console host hands a long burst to the program in chunks further apart than the fixed 300 ms quiet window, so the first Enter landed inside the burst (a trailing newline) and only the retry 4 s later submitted it; the quiet window is now adaptive (above). The retry stays as the fallback, so the lagging-TUI tests accept 1–2 Enters but still require exactly one intact submission. Two test-only races were also fixed: the fixture reported `working` before logging the submission (the test read an empty log after a `confirmed` reply), and it submitted an empty line on an Enter to an empty box and kept the trailing newline, where Codex does neither.

### B2 root cause and fix

Codex sends `PermissionRequest` before the approval prompt and the next hook only when the approved tool finishes (`PostToolUse`); Claude Code's documented hook set likewise has no "permission granted" event (docs only, no real Claude turn). Nothing reported the approval, so the hook `blocked` stayed for the whole command; `review.send` refused it as `AGENT_BLOCKED`.

Fix (fallback, documented in [07 §3.1-6](07-pod-status.md)): podd feeds all terminal input to the status engine. While a hook says `blocked:permission`/`question`, an answer-like key (Enter or a single option key `y a n p 1-9`; not a bare Esc, arrows, focus reports, query replies or pastes) followed by output within 3 s turns the state into `working`, source `heuristic`, confidence 0.6, until the next real hook. Esc behaviour is unchanged (Interrupt hook → idle). The answer time is persisted so a daemon restart does not replay the blocked hook as current. Tests: `pod-status` `answered_permission_prompt_is_working_until_the_next_hook` (Codex and Claude hook sequences), `esc_and_unanswered_prompts_keep_their_behaviour`, `answer_keys`; podd `approved_permission_is_working_and_reviews_queue` (real `pod-hook` PermissionRequest; review refused while blocked; arrow key does not answer; Enter → working/heuristic; review now **queued**; survives a daemon restart).

### B6 root cause and fix

`wait_gate` (and `pod wait`) made one blocking RPC; a closed pipe ended the CLI. Fix (`crates/pod-cli/src/reconnect.rs`): on a lost connection, reconnect to the same pipe with backoff (100 ms doubling to 2 s), never starting a daemon itself, and ask again for the same persisted gate/condition with the remaining timeout; after `POD_RECONNECT_TIMEOUT` seconds (default 60) without a daemon, fail with an error naming the gate. Applies to `pod gate request --wait`, `pod wait --gate`, `pod wait --status/--turn-end` and `pod wait <terminal>`. Test: `waits_survive_a_daemon_restart` (podd killed while a gate wait and a status wait run, restarted 2 s later; approving the same gate ends the waiter with exit 0 and "reconnected" on stderr; the status wait completes; with no daemon returning, a clear error after the 1.5 s window).
